# 자연스러운 한국어 개발 글쓰기

팀원이 바로 이해할 수 있는 한국어로 쓴다. 새 글에도 아래 기준을 적용하고, 기존 글은 어색한 부분만 고친다.

## 개발 용어

- 저장소에서 쓰는 표기와 개발자가 익숙하게 쓰는 용어를 우선한다. 사전 뜻만 보고 번역하지 않는다. Git의 commit은 `커밋`이지 `저지르다`가 아니다.
- 뜻을 설명하거나 용어를 구분해야 할 때만 `의존성(dependency)`처럼 한국어 번역과 영어 원문을 함께 쓴다. 번역이 어색하면 `커밋(commit)`, `리베이스(rebase)`처럼 통용되는 음차를 쓴다.
- 병기는 필요한 첫 등장에만 쓰고 반복하지 않는다. 짧은 제목이나 팀에 익숙한 용어에는 생략한다. API, React, TypeScript처럼 원문이 익숙한 약어·제품명은 그대로 쓴다.
- 코드 식별자, 명령어, 경로, 옵션, URL은 번역하거나 표기를 바꾸지 않는다.

## 윤문 원칙

- **뜻을 지킨다.** 사실, 수치, 부정, 조건, 인과관계와 확신의 정도를 유지한다. 가능성을 확정으로, 권고를 의무로, 예정된 작업을 완료된 작업으로 바꾸지 않는다. 근거·성과·경험을 지어내지 않는다.
- **행동을 바로 쓴다.** “검증을 수행한다”는 “검증한다”로, “설정에 대한 변경”은 “설정 변경”으로 다듬는다. 겹친 피동과 긴 명사 나열을 풀되, 주체를 모르면 임의로 넣지 않는다.
- **내용 없는 말을 덜어낸다.** “주목할 만한”, “획기적인”, “시사하는 바가 크다” 같은 상투적 수식과 반복 요약을 줄인다. 변화와 이유는 원문에 있는 구체적인 내용으로 쓴다.
- **문맥에 맞게 연결한다.** 문장마다 붙은 “또한”, “나아가”, “결론적으로”와 불필요한 “~에 있어서”, “~를 통해”를 덜어낸다. 인과나 대조를 전달하는 표현은 남기며, 특정 단어를 일괄 삭제하지 않는다.
- **글의 성격을 유지한다.** 기존 존댓말·한다체와 문서 형식을 따른다. 억지 구어체, 농담, 감탄, 경험담을 넣거나 어미와 문장 길이를 기계적으로 섞지 않는다. 이미 자연스러운 문장은 그대로 둔다.

## 개발 문서에서 지킬 것

- 커밋과 PR 제목은 변경 내용과 목적을 짧게 쓴다. Conventional Commits의 타입·범위와 저장소의 커밋·PR·이슈 템플릿을 유지한다.
- 스킬과 Spec Kit 문서는 요구사항의 강도, 작업 범위, 완료 조건을 보존한다. 제목, 요구사항·작업 ID, 체크박스 상태, 링크, YAML 키 등 도구가 참조하는 구조를 바꾸지 않는다.
- 절차, 비교, 작업 목록에 필요한 제목·번호·불릿·표는 유지한다. 장식용 강조와 중복 소제목만 줄인다.
- 코드 주석은 의도와 제약을 명확히 쓴다. 윤문 중 실행 코드, 문자열 값, 타입, 린트·타입 검사 지시 주석은 바꾸지 않는다. 직접 인용과 로그 원문도 보존한다.

## 짧은 예시

| 초안 | 다듬은 글 |
| --- | --- |
| `fix: 캐시 초기화를 통해 오래된 응답이 표시되는 문제를 해결` | `fix: 오래된 응답이 표시되지 않도록 캐시 초기화` |
| 해당 옵션에 대한 설정을 수행해야 한다. | 해당 옵션을 설정해야 한다. |
| 이 변경을 통해 오류가 줄어들 수 있다. | 이 변경으로 오류가 줄어들 수 있다. |
| 리베이스는 커밋을 다른 기준 커밋 위에 다시 적용하는 것을 의미한다. | 리베이스(rebase)는 커밋을 다른 기준 커밋 위에 다시 적용한다. |

제출 전 원문과 대조해 의미와 문서 구조가 유지됐는지 확인한다. 요청한 결과물을 우선 제시하고, 별도 요청이 없으면 문장별 진단이나 점수표는 덧붙이지 않는다.
