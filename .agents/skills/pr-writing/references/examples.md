# PR 예시

아래는 가상 사례이며 현재 저장소의 구현·의사결정 근거가 아님. 실제 작성 시 확인한 변경과 기록으로 대체하고 관련 이슈는 본문 맨 아래에 연결.

## 선택 근거를 보충하는 변경

가정: 페이지 설명 요청에 식별자 검사를 추가했고, 요청 취소와의 비교 근거와 응답 순서를 뒤집은 로컬 검증 기록이 남아 있음.

제목: `fix: 페이지 이동 후 이전 설명이 현재 화면을 덮어쓰지 않도록 수정`

````markdown
## Overview

전자책 페이지를 이동하면 늦게 도착한 이전 설명이 현재 화면을 덮어쓰는 문제를 수정했습니다. 마지막으로 요청한 페이지의 응답만 반영하도록 변경했습니다.

## Details

- 페이지 이동과 새 설명 요청 시 요청 식별자를 갱신하고, 현재 식별자와 일치하는 응답만 화면에 반영하도록 수정.
- 이전 요청의 오류와 로딩 종료에도 같은 조건을 적용해 새 요청의 상태를 덮어쓰지 않도록 처리.
- 이전 성공·실패 응답이 늦게 도착해도 현재 설명과 상태를 유지하는 회귀 테스트 추가.

## Additional Comments

요청 취소만으로는 이미 완료되어 후속 처리가 진행 중인 응답을 막을 수 없어 식별자 검사를 채택했습니다. 성공·오류·로딩 종료 처리에 같은 조건을 적용했으며, 핵심 조건은 다음과 같습니다.

```ts
// 요청 시작과 응답 수신 부분 생략
if (requestId !== activeRequestId.current) return
// 현재 요청의 응답만 상태에 반영
```

응답 순서를 뒤집은 로컬 검증에서 이전 응답이 현재 설명과 상태를 덮어쓰지 않는 것을 확인했습니다. 서버의 생성 작업은 중단하지 않으므로, 불필요한 생성 비용이 문제가 되면 서버 취소 지원을 추가 검토할 필요가 있습니다.
````

비교 기록이 없다면 과거 선택 이유를 단정하지 않고 다음처럼 표현.

> 현재 구현 기준 분석: 식별자 검사는 오래된 응답의 화면 반영을 차단합니다. 요청 취소를 추가하더라도 이미 완료된 응답의 후속 처리에는 식별자 확인이 필요합니다.

## 보충 설명이 필요 없는 작은 변경

제목: `docs: PR의 변경 내용과 선택 근거를 구분하도록 작성 기준 정리`

```markdown
## Overview

PR의 목적과 실제 변경을 빠르게 파악할 수 있도록 작성 기준을 정리했습니다. 개요는 짧은 문단으로 요약하고, 구현 내용과 선택 근거는 각각 Details와 Additional Comments에 배치하도록 변경했습니다.

## Details

- `SKILL.md`에 Overview의 1~3문장 문단 형식과 섹션별 문체 기준 추가. Details만 명사형·`~함`으로 끝내도록 지정.
- Details는 실제 변경과 의도를 설명하고, 필요한 대안 비교·한계는 Additional Comments에서 다루도록 역할 구분.
- `references/examples.md`를 같은 문체와 구성으로 수정.
```
