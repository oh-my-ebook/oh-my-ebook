# PR 작성

무엇을 왜 바꿨고 결과가 어떻게 달라졌는지, 코드를 열지 않아도 이해할 수 있게 작성.

## 작성 근거

- `AGENTS.md`, `.specify/memory/constitution.md`, `.github/pull_request_template.md`와 [korean-dev-writing](../korean-dev-writing/SKILL.md) 확인.
- 작업·병합 대상 브랜치는 사용자 지정이나 기존 PR 정보로 확인하고, 로컬 원격 기본 브랜치 참조도 참고. `main`이나 직전 커밋을 임의로 기준 삼지 않으며, 불명확하면 필요한 정보만 질문.
- `git status --short`, `git log <base>..<head>`, `git diff <base>...<head>`로 PR 전체 변경과 관련 코드·테스트·설정 확인. 미커밋 변경은 구분하고 포함 요청이 있을 때 반영 예정 초안으로 작성.
- 해당 기능의 `spec.md`, `plan.md`, `tasks.md`가 있으면 목표·제약 확인. 실제 구현 범위는 diff로 판단하고 명세와의 불일치·미완료도 반영. 명세가 없으면 요청·이슈·코드를 근거로 작성.

## 문체와 구성

- 제목은 대상과 변경 목적이 드러나는 짧은 한국어 Conventional Commits 형식으로 작성.
- 본문은 `Overview` → `Details` → 필요한 경우 `Additional Comments` 순서로 구성하고 템플릿 안내 주석은 삭제.
- Overview와 Additional Comments는 `했습니다`체로 정중한 표현을 사용한다. 현재 동작·제약은 `~합니다`, `~입니다`로 자연스럽게 설명. Details만 `확인`, `구현`, `수정` 같은 명사형이나 `~함`, `~됨`으로 끝내며, 원인과 결과가 이어지도록 작성.
- CI의 검사 목록·통과 결과는 반복하지 않음. 변경 판단에 중요한 검증 결과나 미확인 조건은 Additional Comments에 간결하게 포함. 테스트 코드 변경은 Details에서 목적과 함께 설명.

### Overview

불릿 없이 **1~3문장으로 이루어진 한 문단**으로 작성. 해결할 문제나 변경 목적에서 시작해 변경 후 동작·결과로 연결. 세부 구현 나열은 Details에 두고, 개요만 읽어도 이번 PR의 목적과 전후 차이를 이해할 수 있게 요약.

### Details

실제 파일 변경을 의미 있는 작업 단위로 묶어, **무엇을 어떻게 바꿨고 그 변경이 왜 필요한지** 설명. 코드 수정, 추가 기능, 설정·문서 변경 등을 짧은 불릿이나 문단으로 정리하되 파일 목록이나 diff를 그대로 나열하지 않음.

변경한 책임·처리 흐름·예외 처리·적용 범위 중 이해에 필요한 내용만 포함. 파일명·식별자는 위치나 동작을 설명할 때 사용하고, 선택한 방식과 대안의 비교는 Additional Comments에 배치.

### Additional Comments

검토에 도움이 되는 보충 설명이 있을 때만 사용하며, 없으면 섹션 생략. 불릿을 기본 형식으로 삼지 않고 핵심을 연결한 짧은 문장과 문단으로 구성하며 가급적 2문단 이내로 작성.

선택 이유와 제약, 다른 해결 방법과 채택하지 않은 이유, 감수한 비용·한계, 호환성·배포 시 주의점, 후속 작업과 재검토 조건, 리뷰어가 집중해서 볼 부분 등 이번 PR에 필요한 내용만 포함. 핵심 결정 1~2개를 중심으로 제약 → 선택 → 결과가 이어지게 설명하고, 일반적인 권장 사항을 모두 채우거나 Details를 반복하지 않음.

발췌 코드가 설명에 도움이 되면 언어를 지정한 **10줄 이하 코드 블록** 추가. 원래 동작과 조건을 유지하고 중략·생략 부분은 해당 언어의 주석으로 표시. PoC·실험은 핵심 결론과 선택에 미친 영향만 요약하고, 환경·입력·실행 방법·원본 결과가 있는 자료에 연결.
Poc 및 실험이 필요할 수 있다. 독립적으로 실행 가능한 스크립트로 Poc 및 실험, 측정 등이 가능하다면 별도 프로젝트를 스크립트를 간략히 작성하여 실험 혹은 poc가 가능하도록 만들어 ZIP 파일로 사용자에게 전달한뒤, 이 내용을 활용하라고 제안한다. 현재 개발 환경이 그대로 필요하면 저장소에서 새로운 브랜치를 `poc/<poc 내용 snake-case로 간략히>` 를 만들어, 실험이나 poc를 만든다. 기존 구조를 활용하도록 제안하며, 자료 생성·등록은 요청받은 범위에서만 진행.

## 사실 구분 방법 및 PR에 포함할 수 있는 내용

- 선택·대안 검토·실패 경험은 기록으로 확인된 경우에만 서술. 기록 없는 대안 비교는 `현재 구현 기준 분석`으로 구분하고, 단순 변경에 복잡한 판단을 억지로 추가하지 않음.
- 수치와 효과는 확인된 근거만 사용하고 기대 효과와 측정 결과를 구분. 기대 효과는 확인된 사항이 아니므로 작성하지 않음. 수치는 출처·측정 조건·재확인 경로를 함께 제시하고 전후 비교 조건이 같은지 확인. 실행하지 않은 검사를 성공으로 쓰거나 구현 범위를 실제 사용·운영 성과로 확대하지 않음.
- 코드·명세·자료 링크는 GitHub에서 접근 가능한 경로 사용. 관련 이슈는 본문 맨 아래에 완료 범위면 `Closes #번호`, 일부 범위면 `Refs #번호`로 연결하고 번호를 만들지 않음.
- 제목과 붙여 넣을 수 있는 본문을 제공하고, 작성에 필요한 미확인 정보는 초안 밖에 짧게 표시. 분량과 표현이 불명확할 때만 [PR 예시](references/examples.md) 참고.
- 작성·윤문만으로 코드·명세 수정, 브랜치 변경, 커밋·푸시, 새 실험·자료 생성, GitHub 등록·수정은 진행하지 않음. GitHub 등록·수정까지 요청받았다면 대상 확인 후 처리하고, 결과가 불확실하면 기존 PR을 확인한 뒤 재시도.
